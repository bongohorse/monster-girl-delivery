# MGD Gameplay and Encounters

Turn approved product intent into a complete, verifiable change through the real game path. [AGENTS.md](../../../AGENTS.md) controls authorization and scope. Creating this skill does not authorize changing gameplay, balance or architecture.

## Inputs and routing

Determine the assigned task, approved rule/tuning change, relevant decision state, before/after examples, runtime entry point and acceptance criteria. Read the current rule in [MASTER_SPEC](../../../MASTER_SPEC.md), the relevant sequence/gate in [ROADMAP](../../../docs/ROADMAP.md) when it affects scope, and technical ownership in [ARCHITECTURE](../../../ARCHITECTURE.md). A historical prototype, audit or backlog lesson is supporting context, not a new rule or evidence that a feature is still absent. Verify current source/tests.

This skill leads a rule or encounter change spanning game systems. An individual hazard's movement/collision leads through `mgd-hazards`; presentation-only UI leads through the UI workflow; measuring performance or explaining a regression leads through existing diagnosis/performance guidance. A profiling request alone does not authorize balance changes. A gameplay rule may need UI integration, hazard checks, art or assets as bounded supporting work.

Consult installed skills at execution time. Hazard and acceptance introductions are [PR #506](https://github.com/bongohorse/monster-girl-delivery/pull/506) and [PR #507](https://github.com/bongohorse/monster-girl-delivery/pull/507); UI/performance work is tracked by #500/#503 under [#495](https://github.com/bongohorse/monster-girl-delivery/issues/495). These are not assumed merged/installed dependencies. Art and asset workflows contribute when those outputs change; [#494](https://github.com/bongohorse/monster-girl-delivery/issues/494) remains the shared asset-workflow owner.

## Procedure for an authorized change

1. **Specify the observable delta.** Describe concrete supported before/after scenarios with input, starting state and expected outcome. Distinguish a tunable prototype value from a changed product rule. Identify affected state transitions and downstream values, including any result/reward/record/UI consumers. Clarify only materially unresolved product intent; choose routine reversible implementation details from existing patterns. Do not add a new score contribution, delivery mode or economy merely because the request mentions coins or parcels.
2. **Trace ownership and impact.** Follow the supported input/configuration → authoritative state/rule → qualified event/consequence → presentation/result path. Record who owns updates and consumption, what resets per run and what is retained. For encounter changes trace catalog eligibility, scheduling, lifetime/reservations and live use, not only data construction. Use `graphify` when cross-module relationships remain unclear and verify material findings in current source/tests. Do not create a second event bus, metric store or registration framework to describe existing ownership.
3. **Choose meaningful regression seams.** Use `tdd` for deterministic behavior, `diagnosing-bugs` for defects needing a realistic reproduction, and `codebase-design` only when an abstraction/ownership seam changes. Derive expected results independently under [TEST_QUALITY](../../../docs/TEST_QUALITY.md#core-rule-define-the-expected-result-independently); a hand-counted value or explicit rule often suffices. Exercise public behavior with realistic validated state. A test that copies the production calculation or asserts only a newly added helper's output does not prove integrated behavior.
4. **Implement the smallest complete change.** Reuse current configuration, pure rules, policy adapters and presentation consumption. Wire approved behavior into the actual gameplay path and retire obsolete in-scope paths where needed. Keep input with InputService, time with TimeService, randomness with the existing seeded authority and consequences with gameplay. Reuse suitable existing JavaScript/Web/Phaser capabilities under AGENTS' ownership/determinism constraints; do not replace the logical simulation with a second physics clock. Graphics/UI/configuration edits need no new general framework.
5. **Protect relevant state boundaries.** Check pause/inactive time, restart, death/finalization, repeated event consumption and cleanup where affected. Verify that counts/rewards are awarded once through qualified gameplay events, and that post-death presentation/reveal cannot alter final totals or PRNG state. Use the current [simulation-step policy](../../../ARCHITECTURE.md#5-time-authority-and-simulation-step-policy): select partition evidence when sensitivity is plausible and seeded replay when generation/randomness changes. The current terminal snapshot may retain the enclosing-step endpoint; do not assert exact impact metrics or universal terminal-score equality across frame schedules without an approved contract change. Preserve existing input cancellation and lifecycle boundaries when flight/control wiring changes.
6. **Validate encounter fairness through admission.** For authored segments or multi-hazard combinations, inspect applicable geometry/swept extents, reaction horizon, reachable corridors, transition from the previous encounter, simultaneous warning/lethal windows, readability/pressure limits and protected delivery approaches. Reuse the existing generate → validate → spawn path and policy intersections. Observe rejected/deferred candidates and recovery gaps; a catalog entry or Director-only fixture does not prove AUTO admission. Never loosen hard fairness or mandatory recovery merely to force requested content to spawn. If the intended combination cannot pass current constraints, report the concrete decision and seek a product decision only when materially different rules are needed.
7. **Verify real integration and feel.** Select focused rule/integration/regression checks from the changed paths, and complete [DEVELOPMENT §3](../../../DEVELOPMENT.md#3-required-verification)'s baseline obligations for code/config changes. Choose browser/device/partition/seed/performance evidence using [TEST_QUALITY's matrix](../../../docs/TEST_QUALITY.md#evidence-selection-matrix), without mandatory benchmarks for every rule change. Exercise a representative live scene through the intended entry point. Automated evidence supports its stated domain; it does not establish subjective fun, real touch behavior or visual readability. Required unavailable playtesting stays explicitly pending.
8. **Update the owners and hand off.** Record an approved changed durable product rule in MASTER_SPEC, retaining its actual decision state; update technical ownership only in ARCHITECTURE and commands only in DEVELOPMENT. Do not promote experimental tuning into a final decision. Review the exact diff with `code-review`. Hand the implemented commit/build, before/after behavior, affected paths, tests and their limits, representative seed/scene/replay instructions and open subjective decisions to `mgd-acceptance` when available, or use TEST_QUALITY's existing evidence summary. No agent inspection grants Director approval.

## Example request walkthroughs

These are dry routing examples, not implemented changes or tests performed here. Existing source/test paths are starting points, not a fixed suite.

| Request | Expected treatment and evidence |
|---|---|
| “Change coin valuation.” | Resolve whether the intended change affects pickup value, earned coins or score; the current score formula in PrototypeRunResult uses distance, so pickup value is not automatically a score coefficient. Follow collection qualification through retained counts/value/reward into the immutable run-end snapshot and actual result display, including applicable record consumers. Protect repeated pickup, death-frame ordering and post-death stability where affected. Use hand-counted before/after results, [PrototypeCollectibles tests](../../../tests/systems/PrototypeCollectibles.test.ts), [PrototypeRunResult tests](../../../tests/systems/PrototypeRunResult.test.ts) and the changed scene/display seam. Do not add a records store merely to prove a rule change. |
| “Change the delivery flow.” | Describe allowed state transitions using current ParcelDelivery/route orchestration, including pickup, carrying, handoff/miss, next route and death as relevant. Check completion counting once, preserved run continuation and reward/result consumption under approved rules. Verify restart clears carried parcel/route-local state and restores a fresh-run path; pause/input/cleanup and protected approach remain coherent when affected. Start from [ParcelDelivery tests](../../../tests/systems/ParcelDelivery.test.ts), route tests and [FoundationDeathRetry](../../../tests/game/scenes/FoundationDeathRetry.test.ts), then exercise the changed live route. Do not prebuild deferred delivery modes or parcel physics. |
| “Change an encounter combining several hazards.” | Trace the shared spawn/timing/lifecycle and admission paths, each hazard's actual geometry/lethal phase, then the joint reachability/transition/readability budget and delivery protections. Select affected existing-hazard regressions, plus [LiveEncounterPolicy](../../../tests/generation/LiveEncounterPolicy.test.ts) and [EncounterTransitionValidator](../../../tests/generation/EncounterTransitionValidator.test.ts) evidence where relevant. Validate a reachable representative seeded run and any intended defer/recovery behavior. A pattern passing alone or looking good in a manual fixture does not prove a fair accepted sequence. |

## Completion and output

An authorized gameplay implementation is reviewable when the requested before/after behavior is in the supported runtime path, affected counters/consequences/results and reset boundaries are accounted for, relevant fairness/partition/replay evidence and required checks have results, and any changed canonical rule is recorded with its approved status.

Report the tested commit/build and dirty state when applicable, changed systems, expected versus observed behavior, actual checks and representative playtest/reproduction context. Identify real tool/product/manual-evidence blockers instead of claiming success for an unused helper or pending integration. Subjective Director acceptance remains separate. For this skill-creation issue, completion means documentation/example validation and one focused PR; do not execute these future gameplay changes.
