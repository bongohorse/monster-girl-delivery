# MGD builds and releases

Deliver the requested artifact or authorized publication with traceable identity and truthful test status. [AGENTS.md](../../../AGENTS.md) controls scope and permission. Creating this skill does not authorize running its examples, building artifacts, changing signing/hosting or adding automation.

## Inputs and canonical sources

Determine the requested source/ref, target platform, artifact/test channel or public destination, runtime mode, version and evidence required. Inspect current files and available tools/access before choosing a path. Test-artifact delivery does not authorize a merge, public deployment, GitHub Release or Store distribution. Existing explicit authorization covers the matching action; do not ask again for routine build/check/download/branch/PR work or already authorized publication. Resolve only genuinely missing consequential decisions after completing independent preparation.

[DEVELOPMENT](../../../DEVELOPMENT.md#2-standard-commands) owns commands, [required verification](../../../DEVELOPMENT.md#3-required-verification) and security. [Android distribution](../../../docs/ANDROID_DISTRIBUTION.md) owns test signing, artifact delivery and immutable GitHub Releases; [Capacitor](../../../docs/ANDROID_CAPACITOR.md#local-workflow) owns local packaging; [PWA](../../../docs/PWA_ANDROID.md#hosted-test-build) owns Pages hosting/package checks. [ARCHITECTURE](../../../ARCHITECTURE.md#13-assets) owns technical/asset boundaries; preserve the existing Vite/Bun/Capacitor stack. [MASTER_SPEC §20](../../../MASTER_SPEC.md#20-release-and-online-service-boundaries) owns product release boundaries. [GitHub access](../../../docs/GITHUB_AI_ACCESS.md) describes technical permissions, not authorization. Re-read actual workflow triggers, checkout and build steps rather than inferring capabilities from names or historical reports.

## Existing paths and limits

Inventory inspected at main `97d158bef31ed3a22cbd18fde375973d1cdf7890`; verify against the selected source before execution.

| Requested outcome | Existing entry and constraints |
|---|---|
| Local web artifact/preview | [package scripts](../../../package.json): `bun run build` produces `dist/`; `bun run preview` serves it. [Production config](../../../vite/config.prod.mjs) uses relative URLs. This creates no hosted PR preview or public release by itself. |
| APK for testing | [Android CI](../../../.github/workflows/android-ci.yml) is canonical, supports manual dispatch and path-filtered PR/main builds. It uses Java 25 and locked dependencies, runs Android tests, assembles debug/release, and uploads only the debug APK/evidence for 14 days. It enables `MGD_ANDROID_DIRECTOR_BUILD=1`: production Vite bundling with development/Director runtime enabled, not the normal public runtime. |
| Local Android build | `bun run android:debug` runs `android:sync` then the [Gradle wrapper helper](../../../scripts/android-gradle.mjs). Requires Node plus suitable Java/Android SDK tooling; verify availability. `android:sync` rebuilds web, verifies launcher assets and copies through Capacitor. Copied web assets are generated output, not files to patch. Local compilation does not automatically supply CI evidence or stable signing. |
| Hosted web publication | [Pages workflow](../../../.github/workflows/pages-deploy.yml) builds and verifies the package; PRs only build, without upload/deployment. Main push or manual main dispatch can publish. Rerunning an old eligible run republishes that run's source; choose it only when that exact source is requested. Pages must use Actions publishing; use the existing read/check gate, not a settings change hidden in a build task. |
| Direct Android tester release | [Android Release](../../../.github/workflows/android-release.yml) publishes immutable GitHub Releases for Obtainium from a new package version on main or supported stable tag contained in main. It has no manual dispatch. Requires stable test signing and pinned certificate, validates final APK and preserves evidence (30-day Actions copy plus Release assets). This is a public publication, not an ordinary CI test artifact. |

[Core CI](../../../.github/workflows/ci.yml) owns the standard source checks; packaging workflows do not all run those checks themselves. Check results for the actual built source. Firebase delivery and Play/AAB distribution remain future/manual paths in the distribution document, not installed release jobs. Technical read access does not prove dispatch, signing, Pages or Release permissions; report a denied or unavailable capability precisely without exposing credentials or changing protections.

## Procedure for an authorized build/release

1. **Pin the source and output.** Record full commit, branch/ref, local tracked/untracked changes and requested output before building. Use an isolated clean checkout when producing a clean-commit artifact; do not discard user changes. For an intentional dirty build, describe included changes and label it accordingly. A filename or embedded short hash alone does not prove the packaged tree: [build metadata](../../../vite/buildMetadata.mjs) can use `GITHUB_SHA` before local Git. PR Android CI records the actual checked-out synthetic merge as `builtCommit` and the branch head separately as `prHeadCommit`; retain both, not just the PR number.
2. **Prepare through existing commands.** Use locked dependencies and the selected source's documented toolchain. Include applicable source checks from DEVELOPMENT and existing packaging validation in the actual build path; do not treat unrelated green CI as evidence for this artifact. Inspect asset imports and current generation requirements. [#494](https://github.com/bongohorse/monster-girl-delivery/issues/494) is an open asset-workflow specification at the inspected baseline, not implemented tooling; `assets:build`/`assets:validate` in DEVELOPMENT are planned interfaces. Once implemented, use its owning instructions and integrated build hooks. Until then use actual checked-in assets and approved existing export procedures only where the request requires regeneration; report any missing integration instead of inventing scripts or claiming generation ran.
3. **Choose local or CI execution.** Prefer canonical Android CI for reproducible APK delivery; local web/local Android is useful when the requested artifact and available toolchain fit. Inspect workflow ref, trigger, runtime overrides and side effects before dispatch/rerun/push. Pages on main and version/tag release triggers can publish automatically: a test request must use a nonpublishing path. Retrieve the run for the chosen ref and record run ID/attempt and actual checkout identity. Wait for relevant jobs; a successful dispatch or source check is not a successful build. Keep each output/evidence set together, without mixing old `dist/`, APKs or files from another run.
4. **Verify Android identity and signing when applicable.** Inspect [Capacitor config](../../../capacitor.config.ts), [Gradle configuration](../../../android/app/build.gradle), finished APK badging and signature evidence. Check actual application ID, versionName/versionCode, debug/release state, signing mode and certificate against the intended channel. [Release version helper](../../../scripts/android-release-version.mjs) validates the supported tag/package mapping; release workflow supplies the resulting Gradle values. Debug builds default to versionName `1.0`/versionCode `1` unless overridden: Android CI validating package.json does not mean it applied its version to the debug APK. Stable signing is available only under the existing conditions; PR/non-main CI uses ephemeral debug signing. Missing/partial signing credentials or certificate pin are explicit gaps, not permission to generate/rotate keys or fall back for a release. Keep secrets out of artifacts, logs and handoff.
5. **Check the delivered artifact.** Confirm the downloadable file/URL exists and belongs to the recorded build. Verify provided checksums and Android signature/package evidence. Apply the existing [web package checker](../../../scripts/verify-web-package.mjs) to the actual `dist/` or copied Android web package, as the workflows do; it does not prove every gameplay asset loaded. Check startup/install and requested flows in the available target context under [TEST_QUALITY](../../../docs/TEST_QUALITY.md#evidence-selection-matrix). Separate compilation, package inspection, browser launch, device installation and interaction results. For Pages verify the published HTML/assets and requested build at the real subpath; workflow success alone does not prove the device opened the new version.
6. **Publish only to the assigned destination.** Finish preparation/validation before any genuinely missing authorization question, then use the existing path within explicit scope. A web publication does not authorize Android release, merge or Store delivery. Preserve immutable Android tags/assets and version conventions; never replace an existing release or move its tag to fix a build. Name unavailable permissions, signing or target/version decisions instead of adding a second pipeline. Verify the actual published result and source, not just job submission.
7. **Hand off evidence.** Supply commit/ref and dirty status, mode/platform/version, artifact type and filename, checksum/signature identity where available, run/attempt or local commands/check results, retrieval URL/path and expiry. Distinguish requested branch head from actual built commit. State startup/install/update/device tests actually run and pending acceptance; compose `mgd-acceptance` if available, otherwise use TEST_QUALITY. Artifact expiry does not become permanent distribution; GitHub Release assets are a separate channel. Give real missing capabilities and next decision without implying product approval.

## Dry request walkthroughs

These examples describe future work, not builds, dispatches, publication or device tests performed while creating this skill.

| Request | Expected handling and completion evidence |
|---|---|
| “Create an APK for testing.” | Select source and required runtime mode. Use Android CI or a supported local path; if full Director tooling is inappropriate, flag the default CI mode and choose the existing suitable build path. Deliver the exact debug artifact with build-info/checksum/signature and retrieval/14-day expiry for CI. Identify PR merge versus head when applicable. Do not bump a public version, push a release tag, deploy Pages or promise an Obtainium update merely to provide an APK. State whether installation/launch was actually tested. |
| “Publish the existing web release.” | Apply the already explicit publication authorization to the requested Pages destination/source without a second approval loop. Identify whether the request means current main or an older eligible build; use existing main dispatch or the matching run, not a rerun chosen only by its green status. Check source quality evidence, production mode/package, Pages Actions configuration and final hosted source/URL. The workflow rebuilds from its checked-out source; it does not upload an arbitrary local ZIP. If the requested artifact/source cannot use that path, document the gap before changing hosting or automation. |
| “Provide an update APK.” | Inspect the installed/baseline APK's real ID, versionCode and signer certificate against the candidate. Use the existing stable signed tester-release path when publication is requested, or prepare a suitably signed test artifact within the assigned scope. Same ID and compatible certificate plus appropriate higher version ordering are required evidence; package.json or `stable-test` alone is insufficient. Ephemeral/non-main debug builds and default debug version values cannot justify a generic update promise. Never silently uninstall an existing installation to simulate an update; name reinstall/data-loss implications if relevant. Call in-place update proven only after observing it against the stated installed baseline, recording device and versions. |

## Completion

Complete when the requested artifact or explicitly authorized publication is accessible, matched to its actual source/mode/version, applicable checks have results and missing device/update/acceptance evidence is stated. A successful build may be delivered with clearly pending device evidence when that fits the request; a request requiring a proven install/update remains incomplete until that observation exists. Documentation-only skill creation ends with documentation/example validation and its own PR.
