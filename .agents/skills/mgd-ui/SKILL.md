# MGD UI

Deliver the requested UI flow in its actual game/platform context. [AGENTS.md](../../../AGENTS.md) controls scope and permissions. Creating this skill does not authorize implementing its examples, selecting a framework or changing the visual style.

## Inputs and routing

Identify the target screen/control and UI layer, intended task, authoritative state source, supported inputs/platforms, relevant states and acceptance criteria. Inspect existing components, layout, typography/graphics and interaction patterns before choosing implementation. A current Director decision and the assigned Issue control intent; historical screenshots or experimental graphics do not establish a design system.

UI leads presentation and control behavior. A changed scoring, delivery or other game rule leads through gameplay; UI consumes the result. Graphic creation/revision uses `mgd-art`, export/runtime media preparation uses `mgd-asset-integration`, and review evidence uses `mgd-acceptance` when actually available. Their introductions are separate [#495](https://github.com/bongohorse/monster-girl-delivery/issues/495) tasks ([art PR #504](https://github.com/bongohorse/monster-girl-delivery/pull/504), [assets #505](https://github.com/bongohorse/monster-girl-delivery/pull/505), [acceptance #507](https://github.com/bongohorse/monster-girl-delivery/pull/507), [gameplay #508](https://github.com/bongohorse/monster-girl-delivery/pull/508)); do not assume those PRs merged. Consult current Art Direction/reference status if available, without inventing palette or production approval.

## Procedure for an authorized UI change

1. **Define the flow and state source.** Describe what the user does and what observable outcome changes. Select applicable visible/hidden, enabled/disabled, paused, run-ended, loading/empty/error states; do not manufacture every state for a static label. Identify whether the control sends intent through an existing callback/service or only displays values. Resolve materially open product behavior; choose routine presentation details from existing patterns.
2. **Fit the existing layer and layout.** Use the current UI technology and layout/scale ownership. Derive placement from the relevant viewport/safe area and distinguish logical units, canvas backing pixels and CSS/device pixels. Check affected aspect ratios and text lengths/numeric ranges, readability, contrast and practical touch targets at actual display size. Keep important controls within safe areas without covering gameplay dangers. Preserve applicable text resolution/sharpness and font/icon identity. A text correction needs its affected layout, not every possible device; a layout/input change may need broader representative sizes. Do not build a new design system or rescale gameplay merely to fit a panel.
3. **Wire intent without leakage.** Follow the existing control/input path, propagation and explicit gameplay blocking. Test matching active pointer identity, release/outside-release/cancel and lifecycle interruption when relevant; repeated taps or held keys must not produce unintended duplicate actions. Hidden/disabled controls must not accidentally act. Preserve other active UI blocking and avoid clearing a block that the control does not own. For keyboard-capable controls inspect key repeat, game-key conflicts, focus/navigation and restoration. DOM controls need their actual focus and browser propagation behavior; canvas controls do not gain DOM focus semantics automatically. Use the supported browser/native Back/Escape flow when present or requested; do not invent global navigation or assume Android Back already has an app handler.
4. **Keep display and gameplay ownership separate.** Read authoritative values and snapshots. Result animations/reveals may change what is shown, not the final score, reward, delivery count or RNG. A Director adjustment uses its existing tuning/action callback and validation, not a copied gameplay formula. Preserve the affected development/Director or optional production-diagnostics gating and cheap diagnostics. If the requested UI implies a new product rule or persistence contract, route that part through its owning task rather than hiding it in a button handler.
5. **Account for lifecycle and cleanup.** Inspect show/hide, scene shutdown/recreation, restart and relevant page/app interruptions. Cancel held interaction and remove owned game-object, scene, canvas/window listeners and captures. Destroy UI objects and release only the relevant interaction state. Resume must respect existing lifecycle reasons and normalized time; a click must not resume an app still blocked by another reason or leave thrust held. Check cleanup only for mechanisms actually used; do not introduce timers/listeners just to satisfy a checklist.
6. **Check the real context.** Run the supported interaction and observe the result, not just a screenshot or mocked listener count. Choose focused existing tests for project-owned layout/state/input contracts; use `tdd` for deterministic behavior and `diagnosing-bugs` for failures needing reproduction. Follow [DEVELOPMENT §3](../../../DEVELOPMENT.md#3-required-verification)'s baseline for code/config changes and [TEST_QUALITY](../../../docs/TEST_QUALITY.md#evidence-selection-matrix) for browser/device evidence. An agent screenshot can show layout; it does not prove touch ergonomics, navigation or device lifecycle. Record exactly which states/viewports/input sources were tested and which required checks remain unavailable.
7. **Review and hand off.** Review the exact diff with `code-review`; keep any durable product-rule/technical changes in their owning docs. Provide the changed flow, authoritative sources, tested commit/build and dirty status, platform/viewports, interaction steps/results, visual evidence where useful and pending device/Director criteria to acceptance. For small copy changes, keep evidence proportional. Passing tests or inspection does not supply Director visual/feel approval.

## Dry request walkthroughs

These are decision examples, not implemented UI changes or device tests.

| Request | Expected handling and evidence |
|---|---|
| “Change the pause button.” | Locate the actual target control first; inspected main `97d158bef31ed3a22cbd18fde375973d1cdf7890` has lifecycle pause infrastructure but no established user pause button assumed by this skill. If the task actually requires a new control, name the missing integration and resolve only material pause/resume intent. Follow the existing lifecycle/time owners rather than a second pause flag. Check UI pointer/Space leakage, interruption/cancellation, repeated activation, held-input release, relevant hidden/paused states and resumption while other pause reasons apply. Use [InputService](../../../tests/input/InputService.test.ts), [LifecycleService](../../../tests/core/LifecycleService.test.ts) and the actual changed scene/control seam, plus live interaction and device checks where required. |
| “Extend the result display.” | Read the immutable run-end snapshot and existing fail/retry phase; clarify whether the requested field already exists or needs a separately scoped gameplay change. Fit longer labels/larger values on affected layouts and keep one-action retry/reveal behavior coherent. Observe the display through run end and retry; protect final totals from animation or repeated input. Start with [FoundationDeathRetry](../../../tests/game/scenes/FoundationDeathRetry.test.ts), result snapshot tests and the changed layout seam. |
| “Add a Director control/panel.” | Choose the affected existing surface first: Panel/Tuning/Run controls use Phaser; PerformanceHud uses DOM. Reuse its components, responsive placement, mode/build gating and service callbacks. Identify whether the panel is read-only diagnostics or intentional tuning/action UI. Exercise only the inputs the control supports, propagation/blocking and pointer cancellation; verify hide/show and teardown/restart. Start from [DirectorPanel](../../../tests/devtools/DirectorPanel.test.ts), [DirectorTuningControls](../../../tests/devtools/DirectorTuningControls.test.ts) and [DirectorResponsiveLayout](../../../tests/devtools/DirectorResponsiveLayout.test.ts). Use [PerformanceHud tests](../../../tests/devtools/DirectorPerformanceHud.test.ts) for its DOM path. Do not switch UI layers or add universal keyboard navigation or a framework merely because the example is called a panel. |

## Completion and output

An authorized UI change is complete when the requested flow is connected to its real state/intent source, affected layout and input states have results, relevant cleanup/gating is preserved, applicable checks have passed and real blockers or manual acceptance gaps are stated. Report only the actual tested states and build; a visible control with no executed action is not proof of correct operation. Documentation-only skill creation ends with documentation/example checks and its focused PR, without implementing these future UI tasks.
