# MGD Asset Integration

This skill applies the asset workflow; it does not implement a pipeline. Follow [AGENTS.md](../../../AGENTS.md) for scope and authorization. [#494](https://github.com/bongohorse/monster-girl-delivery/issues/494) owns the shared workflow contract. If its implementation has introduced `docs/ASSET_WORKFLOW.md`, read that canonical source and its current commands; do not maintain a competing schema or build system here.

## Inputs and routing

Identify the source file, provenance/rights information, approved visual variant and reference, stable asset ID (existing ID for replacement), target use, processing recipe/profile, display size/render context, intended **prepared** or **active** use, and requested outcome: candidate inspection, active replacement or new integration. A human filename such as `bunter beachvolleyball.jpg` identifies the source, not automatically a technical import ID. Use the implemented ID validation and collision rules; do not invent a slugging scheme in this skill.

For visual revision or background removal, use `mgd-art` and `docs/ART_DIRECTION.md` when available. Their introduction is tracked in [#496 / PR #504](https://github.com/bongohorse/monster-girl-delivery/pull/504), separate from this skill. Preserve recorded trial/draft status rather than treating art as production-approved. An explicitly unchanged-image request preserves its background; JPG cannot carry transparency. Conversion alone does not remove a background.

For new behavior, hazards or gameplay lead; image integration contributes preparation and presentation. Consult the actual skill catalog: hazard #498, gameplay #499 and acceptance #501 are separate tasks under [#495](https://github.com/bongohorse/monster-girl-delivery/issues/495), not presumed installed dependencies. Reuse [loading-assets](../loading-assets/SKILL.md) and [sprites-and-images](../sprites-and-images/SKILL.md) for actual Phaser wiring; use existing diagnosis/test/review skills only when their triggers apply.

## Verify the available route first

Inspect the current checkout, #494's implementation status, `package.json`, the relevant source/export notes and actual loader/presentation code. [DEVELOPMENT.md §11](../../../DEVELOPMENT.md#11-asset-commands) distinguishes planned commands; [ARCHITECTURE.md §13](../../../ARCHITECTURE.md#13-assets) owns technical stages; [MASTER_SPEC.md §15](../../../MASTER_SPEC.md#15-asset-production-principles) owns product constraints.

**Baseline inspected on 2026-09-29, main `97d158bef31ed3a22cbd18fde375973d1cdf7890`:** no shared prepare/build/validate/preview scripts, generated registry or `docs/ASSET_WORKFLOW.md` exist. The `assets:*` interfaces in #494 are planned; do not run them or claim their guarantees until implementation is verified. Do not turn a request to use them into an implicit implementation of #494.

The supported legacy spike route is documented in [its source notes](../../../assets/source/district-01/hazards/README.md): source artwork and an asset-specific Python/Pillow exporter produce the committed runtime PNG. The exporter writes directly to the live `public/assets/m6/` destination; it is **not** an isolated preview or general importer. Its crop, sampling and canvas choices are only that trial's recipe. [Preloader](../../../src/game/scenes/Preloader.ts) loads the `molten-spike-trial` key, [MoltenSpikePresentation](../../../src/entities/MoltenSpikePresentation.ts) consumes it, and [the live catalog test](../../../tests/generation/M6MoltenSpikeTrial.test.ts) covers entry into the seeded run. These inspected paths establish existing wiring, not new runtime/device test results.

For a legacy request within supported scope, use those actual paths and retain the original source and exporter version in Git. A candidate-only request must not invoke the direct-to-runtime exporter in the active checkout. If a legacy candidate export is necessary, use an isolated checkout containing the same source and exporter, clearly label its output as a candidate, and leave the active checkout untouched. This does not provide the missing shared prepare API, state schema or registry. For an unsupported new asset/profile, report the concrete missing tooling; proceed only with an expressly authorized existing manual integration path, documenting its limitations. Do not add a builder, metadata system or lock mechanism to fill the gap.

## Procedure for future asset requests

1. **Resolve identity and recipe.** Distinguish creation from update of an existing ID and retain original bytes/history. Record the chosen source, any separately authorized edited source, profile and effective recipe in the workflow's existing authoritative locations. Include provenance and any unresolved rights information. Resolve trim/padding, orientation, pivot, sampling, aspect ratio, canvas and target resolution from actual presentation needs. Distinguish source pixels, texture pixels, logical units and screen/backing pixels. Preserve a source anchor through crop/scale/padding; do not accidentally recenter it. The legacy exporter itself is its reproducible recipe; do not fabricate a new metadata format.
2. **Prepare a candidate.** When implemented, use the documented combined prepare invocation and supported arguments from #494's owning documentation. It imports/updates or prepares an existing ID, validates and produces a candidate preview; it does not activate or publish. Follow #494 §12.2's single-writer/shared protection contract, including finite consumers and restart handling. Do not add another lock, bypass a reported conflict or recover a lock from age alone. Separate checkouts are independent. Until that protection exists, serialize legacy writes explicitly and avoid racing an exporter with a build or active server; report the missing automated guarantee.
3. **Inspect the precise output.** Show original versus candidate at target size and enlarged detail, light/dark/checkerboard alpha views, canvas/visible bounds/pivot, dimensions and relevant size measurements using available tools. Show asset ID, candidate versus runtime, profile, target size/render factor and fingerprint. Use #494 §12.1's source/effective-recipe/profile/builder/toolchain identity plus export hashes; record the actual generator versions. For legacy output, retain source/exporter/export hashes and Python/Pillow versions as traceable inputs and clearly note the absence of the shared fingerprint/report implementation. Recheck inputs and expected output hashes before relying on a preview. A source/recipe/toolchain or relevant integration change invalidates old evidence; a stale image is not repaired by relabeling it.
4. **Activate only the intended content.** A preview of a prepared asset stays outside the active runtime set and cannot alter its registry, media or other assets. For activation or active replacement, use the workflow's explicit state transition and full runtime build, as distinct from candidate preparation (#494 §§7.1, 12.3). Replacing an active source leaves its current runtime output stale until a successful full build. Never publish one candidate into the registry as a substitute for that build. Follow the implemented server stop/restart contract for full runtime replacement; do not promise live Phaser texture reload. In the legacy route, a request to integrate authorizes explicit source/export/loader/presentation changes within scope; describe manual inclusion rather than pretending a managed activation state exists.
5. **Prove actual use.** Trace source → current export → registry/import or legacy URL → load key/frame → reachable scene/presentation. Verify the built package and relevant deployment subpath, loader success and expected visible instance with risk-appropriate evidence. Registration, a file under `public/`, or a mocked load call alone does not prove live integration. For a fresh checkout, establish the documented dependency/export/build route without relying on ignored local outputs or caches; report any missing stage rather than claiming reproducibility from a warm checkout. Use the current commands from DEVELOPMENT, not planned asset APIs.
6. **Check presentation against interaction.** For crop/scale/pivot/flip changes, compare the visible interactive region with the existing authoritative geometry at target size and relevant movement/rotation/warning states. Use actual gameplay/Director geometry, not an alpha-derived hitbox. Keep image checks separate from collision, pickup, delivery or input evidence. Hand those claims to the hazard/gameplay/input owner and relevant tests under [TEST_QUALITY.md](../../../docs/TEST_QUALITY.md); modify gameplay geometry only when that change is explicitly in scope. An unchanged hitbox alone does not establish fair visual correspondence.
7. **Retain minimal review evidence.** Apply #494 §§15.1–15.2: retain the accepted comparison, fingerprint/export hash and actual tested integration commit/build, with context, reviewer, result and decision link. Include an ingame screenshot and motion observation/clip when needed for the claim; a prepared candidate needs no ingame evidence and is not integrated. Agent inspection and Director acceptance are separate. The planned permanent evidence location from #494 is used when warranted by an actual acceptance; do not invent accepted evidence or create an empty archive now. An expiring CI artifact alone is not durable evidence. Report checks and acceptance still pending.

## Deactivation and removal

Age is not grounds to remove a source or export. For an explicit deactivation/removal request, inspect actual registry, loader, scene and presentation consumers, replace/remove runtime references, and follow #494 §7.1's transition/full-build procedure when implemented. Text search alone does not prove reference freedom. Retain sources, accepted evidence and still-needed legacy content; cleanup touches only workflow-owned generated output. Source deletion requires its own authorized removal scope.

## Completion and output

Return source and ID, recipe/profile or legacy exporter revision, output/preview location and fingerprint/hash evidence, prepared/active intent and actual managed/manual integration status, checked loader/presentation path, comparisons/tests actually performed, acceptance status and concrete remaining gaps. Run [DEVELOPMENT.md's required checks](../../../DEVELOPMENT.md#3-required-verification) for code/config changes and select additional runtime/device evidence under TEST_QUALITY. Documentation-only work needs applicable documentation checks. A candidate preview can complete a preview request; an integration request needs evidence of actual game use or an explicit unresolved blocker.

## Request walkthroughs

These are dry routing examples, not completed imports or acceptance evidence.

| Request | Expected handling |
|---|---|
| “Show the prepared ball, without adding it to the game.” | Resolve the existing ID and candidate recipe; use isolated prepare/preview if implemented. With only legacy tools, inspect existing candidate/source or export in an isolated checkout if supported. Active registry/runtime remain untouched; missing ball tooling is reported. |
| “Replace the active spike with this updated image.” | Target the existing ID, retain source history, inspect the new candidate and treat the old runtime export as stale. Use full managed build or the verified legacy exporter/manual route, then check loading, actual presentation and visual geometry correspondence. |
| “Integrate `bunter beachvolleyball.jpg` as a bouncing hazard.” | Gameplay/hazard leads behavior. Resolve a stable technical ID and permitted background treatment; prepare/integrate the image without inventing behavior from metadata. Separate visual/loader proof from bounce/collision tests. Missing shared import tooling is a documented gap. |
| Fresh checkout, parallel preparation/build, or old preview after a source edit | Verify dependencies and complete current outputs; follow the existing writer/consumer contract or serialize legacy work. Rebuild/reinspect stale output and invalidate mismatched evidence. Do not add automation or a second lock. |
